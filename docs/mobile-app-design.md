# Lumino Android App 功能迁移设计（审核稿）

状态：待用户审核

本文只设计独立 Android 客户端。允许为 AI、MCP 和文档解析增加后端/数据库能力，但必须保持现有 Web 页面、既有 API 行为和线上部署稳定。Android 客户端位于 `mobile-app`，使用 uni-app Vue 3，由 HBuilderX 打包。

## 1. 产品定位

Web 端的核心任务是公开展示与内容管理；Android 端的核心任务是登录用户高频使用自己的数字庭院。因此 App 采用“私密优先、公开内容保留”的策略。

- 未登录：进入公开前厅，可以浏览个人介绍、书房、博客，并登录或申请加入。
- 已登录：默认进入“庭院”总览，不再把公开博客作为第一入口。
- 博客不删除、不下线，只从 App 的一级导航降为前厅公开内容；新增后端能力必须向后兼容既有博客接口。
- “内院”保留为品牌概念，但拆成庭院总览、空间、记录、聊天和自律等可理解的功能模块。

### 1.1 书房与私人收藏的边界

当前 Web 的“书房”是站点公开资料，不是每个用户自己的私密书籍库：

- `SiteProfile.media_cards` 由超级管理员在站点资料中维护，包含书籍、影视、音乐、生活片段和其他收藏。
- 公共接口 `/api/site/profile` 只返回 `is_public=true` 的媒体卡片，因此访客和登录用户看到的是同一套公开书房内容。
- 用户注册时会自动拥有个人空间，但个人空间目前的数据模型是空间记录、相册和成员，不包含独立的私密书籍条目。
- 在“不改 Web 前后端”的约束下，Android 首版不虚构一个会与 Web 同步的私密书籍库。

如果以后需要私人阅读库，有三个选择：

1. 继续把书房作为公开展示，私人阅读心得写入个人空间记录；这是当前版本的推荐方案。
2. Android 本地保存“我的收藏”；实现快，但不能跨设备同步，也不会出现在 Web。
3. 未来新增私密书籍模型和 API；这需要后端和数据库变更，不放入本次迁移范围。

## 2. Android 底部导航

根据“用户体验优先”和 AI 创作中枢的定位，首版底部只保留四项：

| 底部项 | 登录后首页 | 主要内容 | Web 来源 |
| --- | --- | --- | --- |
| 前厅 | 公开内容首页 | 个人介绍、精选博客、书房入口、最近公开内容 | `/`、`/library`、`/blog` |
| AI | AI 工作台 | AI 聊天、会话、附件、多模态创作、发布预览 | `/chat`、MCP 工具 |
| 空间 | 私密空间列表 | 创建/加入空间、空间文章、相册、成员和设置 | `/spaces`、`/spaces/[id]` |
| 我的 | 账号中心 | 个人资料、权限状态、设置、退出、管理入口 | `/auth/me`、管理入口 |

书房不再成为底部按钮，而是通过前厅的“我的收藏/书房”卡片和“我的”中的内容入口访问。博客保留在前厅中作为公开内容，但不抢占 AI、空间和账号的一级操作位置。

未登录时四项显示为“前厅 / AI / 空间 / 我的”，其中 AI、空间和我的会在需要登录时进入登录引导。登录后底部结构保持不变，避免登录前后按钮位置跳动。

### 2.1 前厅

前厅是公开展示和内容发现页，不承担私人工作台职责：

- 顶部保留 Lumino 个人介绍和站点气质。
- 主卡片显示精选博客、最近公开文章和书房入口。
- 书房入口展示公开书籍、影视、音乐和生活收藏。
- 登录用户可以从前厅进入 AI、空间和我的，但不会在前厅堆放私密数据。

### 2.2 AI 工作台

AI 是 Android 端的核心入口，分为“聊天”和“创作发布”两种模式：

#### A. AI 聊天

- 会话列表：新建、重命名、删除、最近使用排序。
- 会话页：模型选择、消息流式输出、图片附件、每日次数限制和错误恢复。
- 输入栏支持文字、图片、文件；附件在发送前显示缩略图、文件名、大小和移除按钮。
- AI 回复中的内容可以一键进入“生成文章”流程，而不是要求用户重新复制粘贴。

#### B. 多模态创作发布

用户点击“生成文章”后，进入四步流程：

1. **收集素材**：输入主题、目标读者、语气、关键词；选择图片、Word、PDF、Markdown 或已有聊天内容。
2. **AI 生成**：先生成标题、摘要、正文、标签和封面建议；用户可以继续对话修改。
3. **选择去向**：选择“公开博客”“空间文章”或“仅保存草稿”。
4. **预览确认**：显示最终渲染效果、可见范围、作者身份和附件清单；用户明确点击发布后才写入目标位置。

目标去向的权限规则：

| 目标 | 普通用户 | 博客编辑用户 | 超级管理员 |
| --- | --- | --- | --- |
| AI 聊天 | 可以 | 可以 | 可以 |
| 空间文章 | 仅能写入自己加入且有权限的空间 | 同左 | 同左，另可管理所有空间权限 |
| 博客草稿 | 不可 | 可以创建自己的草稿 | 可以 |
| 公开博客 | 不可 | 可以公开自己的文章 | 可以公开所有文章 |
| 首页精选 | 不可 | 不可 | 可以 |

空间文章使用现有空间记录模型，保存为 `Note`；公开博客使用现有 `BlogPost` 模型。两者在 AI 预览页明确标注“公开博客”或“仅空间成员可见”，防止误发。

### 2.3 空间（内院总览）

空间页是 Android 端的私密内院工作台，不做成 Web 的大段介绍页：

- 顶部显示头像、昵称、问候和当天日期。
- 第一张卡片显示今日自律摘要；没有授权时显示申请权限或暂不可用。
- 第二张卡片显示最近使用的私密空间。
- 快捷操作：新建空间记录、打开聊天、今日打卡、进入相册。
- 底部显示最近更新的记录和一篇博客精选，但不让博客占据主视觉。
- 管理员只额外显示“管理后台”入口，普通用户完全不显示。

空间是内院中最重要的实际功能，采用两级结构：

1. 空间列表：个人空间、情侣空间、家庭空间、挚友空间；支持创建和邀请码加入。
2. 空间详情：空间摘要、成员、相册、记录、空间设置。

空间详情内部使用顶部二级 Tab 或分段控件：

- 概览：空间名称、描述、成员数和最近内容。
- 相册：相册列表、创建相册、照片上传、照片预览和删除。
- 记录：记录列表、新建记录、编辑锁、只读提示和删除。
- 成员/设置：邀请、移除成员、容量、基本信息和删除空间。

### 2.4 书房

书房承接所有公开内容，但按用户价值排序：

- 第一层：个人资料和书籍、影视、音乐、生活收藏。
- 第二层：博客分类、精选文章、搜索和文章详情。
- 文章详情保留 Markdown、代码块、图片、目录和返回位置。
- 有写作权限的用户在“我的”或书房右上角看到文章管理，不占用普通用户导航。

### 2.5 我的

我的页面包括：

- 当前用户头像、昵称、邮箱和账号状态。
- 自律权限、博客写作权限、创建空间权限等权限说明。
- 主题、通知、缓存清理、关于 Lumino、隐私说明。
- 退出登录。
- 超级管理员显示管理后台入口；普通用户不显示管理菜单。

### 3.1 公开功能

| Web 页面 | Android 设计 |
| --- | --- |

| `/library` 书房 | 书房首页，媒体卡片改为横滑卡片和详情弹层/详情页。 |

| `/courtyard` 内院入口 | 未登录时作为登录引导；已登录进入 Android 的空间/内院总览。 |

| Web 页面 | Android 设计 |

| `/spaces` | 空间列表、创建空间、邀请码加入。 |

### 3.3 写作与超级管理员功能

这些功能不进入普通用户底部导航，只按权限从“我的”进入：

| Web 页面 | Android 设计 |
| --- | --- |
| `/blog/manage` | 我的文章、草稿/发布状态、设为精选、撤回、删除和分类管理。 |
| `/blog/write` | 移动端 Markdown 写作，编辑与预览采用上下切换；图片通过现有上传接口。 |
| `/admin` | 管理后台首页，使用分组卡片而不是桌面多栏布局。 |
| `/admin/profile` | 站点资料、头像/封面、链接、状态、媒体收藏编辑。 |
| `/admin/analytics` | 访问趋势、来源页面、设备、地域字段和时间范围筛选。 |

管理员后台继续覆盖现有功能：用户启停、空间/自律/博客权限、系统配置、邀请代码、存储配额、博客导入与管理、AI 连接测试/模型检查、博客和书房 MCP Token。它们是低频管理功能，优先保证可用，不追求与 Web 管理后台一比一视觉一致。

博客作者权限与超级管理员的公开可见性规则保持一致，但管理范围不同：

- `can_write_blog=true` 的作者可以创建和管理自己的文章。
- 新文章默认不是公开、不是已发布；作者需要分别将文章设为公开并发布。
- 公开博客接口只返回同时满足 `is_public=true` 和 `is_published=true` 的文章，因此作者文章一旦完成这两个状态，访客看到的展示方式与超级管理员文章相同。
- 只有超级管理员可以管理所有作者的文章、管理分类、导入 Markdown、删除他人文章和设置首页精选。

## 4. 现有 API 复用方案

后端接口保持不变，Android 只增加一层请求适配器：

| API 组 | Android 用法 |
| --- | --- |
| `/api/auth/*` | 登录、注册、刷新、退出和当前用户。使用 HTTPS 和原有 HTTPOnly Cookie。 |
| `/api/site/*` | 公开站点资料；管理员资料编辑继续复用原接口。 |
| `/api/blog/*` | 博客列表、精选、分类、详情和写作管理。 |
| `/api/spaces/*` | 空间、成员、邀请码、容量、相册和记录。 |
| `/api/chat/*` | 会话、模型、消息和流式输出。 |
| `/api/discipline/*` | 健康档案、打卡、AI 分析、报告、Apple Health 导入和快捷同步。 |
| `/api/upload` | 头像、封面、照片、饮食图和运动图上传。 |
| `/api/admin/*` | 仅 root 用户显示和调用。 |

## 5. MCP 与多模态发布设计

### 5.1 当前 MCP 能力

现有服务挂载在 `/api/mcp/blog` 和 `/api/mcp/library`，Android 端在此基础上增加一个后端编排层：

- 博客 MCP：列出分类、上传图片、创建/更新博客、发布博客。
- 书房 MCP：读取和维护超级管理员的公开/隐藏书房资料、收藏卡片和链接。
- MCP 通过超级管理员签发的 Bearer Token 识别作者；博客 Token 绑定 `author_id`，并有 `allow_auto_publish` 开关。
- 现有 MCP 只支持图片上传，不解析 Word、PDF 或其他办公文件。
- 现有 MCP 没有空间、相册或空间记录工具。

### 5.2 后端控制 MCP 权限，Android 只显示有权限的功能

MCP Token 相当于长期发布凭据，不放进 APK，也不让用户手工复制。由后端管理员配置权限，Android 通过登录态读取能力结果：

- 管理员在后台为用户启用/停用“AI/MCP 创作”权限。
- 数据库新增 `users.can_use_mcp` 用户级开关，默认关闭；超级管理员可按用户开启，root 用户按有效权限自动拥有能力。
- 现有 `MCPBlogToken.author_id`、`allow_auto_publish`、`is_active` 继续作为博客 MCP 的细粒度控制。
- 新增 Android 能力查询接口，例如 `/api/ai/capabilities`，只返回 `can_chat`、`can_generate`、`can_publish_blog`、`can_publish_space`、`can_mcp_publish` 和 `allow_auto_publish`，绝不返回 Token。
- Android 只有在 `can_mcp_publish=true` 时显示“MCP 发布”入口；无权限用户看不到按钮，也不能通过深链进入。
- Android 调用新的鉴权编排接口，由后端在服务端调用 MCP 工具或共享服务层；客户端只携带正常登录态。

推荐的后端编排接口：

| 接口 | 作用 | 权限 |
| --- | --- | --- |
| `GET /api/ai/capabilities` | 返回当前用户 AI、MCP、博客和空间能力 | 登录用户 |
| `POST /api/ai/ingest` | 接收素材并创建解析任务 | 登录用户 |
| `GET /api/ai/ingest/{id}` | 查询素材解析状态和结果 | 素材所有者 |
| `POST /api/ai/drafts` | 保存 AI 草稿、目标和素材引用 | 登录用户 |
| `POST /api/ai/publish/blog` | 通过后端编排调用博客发布能力 | 博客权限/MCP 权限 |
| `POST /api/ai/publish/space` | 通过后端编排创建空间记录 | 空间成员和写入权限 |

这样可以真正做到“后端开关控制 MCP 发布功能可见”，同时不把高权限凭据下发到 Android。

### 5.3 Word、PDF 和图片的处理链

综合 Android 包体积、服务器 2C2G 资源和实际使用，采用“客户端预处理 + 后端受控解析”的混合方案：

| 素材 | 首选处理 | 原因和限制 |
| --- | --- | --- |
| 图片 | Android 本地压缩、旋转修正后上传 | 减少流量和图床压力；原图不默认永久保存 |
| Markdown/TXT | Android 本地读取，直接进入 AI 上下文 | 成本低、速度快 |
| DOCX | 后端解析文本和内嵌图片 | 兼容性比在 App 内打包完整 Office 解析器更好 |
| PDF 文本型 | 后端提取页文本，按页/段落分块 | 解析稳定，便于控制上下文长度 |
| PDF 扫描件 | 默认提示需要 OCR；只对用户选定页做 OCR | OCR CPU 和内存成本高，不默认全量执行 |
| DOC 旧格式 | 首版提示转换为 DOCX/PDF | 依赖原生转换器，避免 APK 体积和兼容风险 |

后端解析策略：

- 新增 `ai_ingest_jobs` 表，记录用户、文件名、类型、大小、状态、提取文本、图片引用、错误和过期时间。
- 原始 DOCX/PDF 只进入临时目录，解析完成或超时后删除；数据库保存提取结果和必要的图片 URL，不默认保存原文件。
- 小文件即时解析：DOCX 不超过 5 MB、PDF 不超过 10 MB 且不超过 20 页时，优先在请求内完成。
- 大文件异步解析：超过即时阈值但未超过单文件上限时，返回任务 ID；Android 展示进度并轮询状态。建议单文件上限 DOCX 20 MB、PDF 30 MB、最多 100 页。
- 后端使用轻量文本解析库；不在首版引入全量 Office 转换服务或全量 OCR。
- 解析结果进入 AI 上下文前按章节/页分块，支持用户选择“全文摘要”“指定页”或“只提取要点”，避免一次请求撑爆模型上下文。

生成过程必须保留“原始素材”和“AI 草稿”的区分。用户点击发布前可以查看、删除或重新生成，避免把未经确认的图片和文档内容公开。

### 5.4 文章发布状态机

```text
素材选择
  -> AI 草稿
  -> 用户修改
  -> 选择目标（博客 / 空间 / 仅草稿）
  -> 权限检查
  -> 预览确认
  -> 保存草稿或发布
  -> 成功页（含可见范围和链接）
```

- 博客编辑用户：默认保存草稿；公开发布需要一次明确确认。
- `allow_auto_publish=false` 的 MCP Token：只能生成/更新草稿，不能直接公开。
- `allow_auto_publish=true` 的 MCP Token：可以执行自动发布，但 App 仍展示发布结果和撤回入口。
- 空间文章：只能进入当前用户有成员资格的空间，默认对空间成员可见，不进入公开博客。

### 5.5 Android 与 Web 的同步规则

Android 新增的内容不另建一套孤岛数据：

- Android 发布到博客的内容写入现有 `BlogPost`，Web 博客列表和文章详情会立即按公开状态显示。
- Android 发布到空间的内容写入现有 `Note`，Web 空间记录页会立即显示，成员权限和编辑锁继续由后端统一处理。
- Android 上传到相册的照片继续写入现有相册接口，Web 端同步可见。
- AI 会话、素材解析任务和草稿属于新增能力，可以增加独立表和接口；在 Web 没有对应页面前，不强行改变 Web 页面。
- 如需 Web 后续查看 AI 草稿，只需新增 Web 入口，不改变既有博客和空间页面的数据协议。
- 建议在新增草稿/文章元数据中保留 `source=android_ai` 和 `source_mcp`，作为审计信息，不影响现有 Web 展示。

## 6. 后端兼容与技术问题

### 6.1 登录 Cookie

当前后端登录成功后通过 `access_token` 和 `refresh_token` Cookie 鉴权。Android App 使用 `uni.request` 直接访问 HTTPS API，并依赖 App 的 Cookie 管理；不能照搬 Web 的 Next.js rewrite。登录、重启 App、过期刷新和退出必须在真机验证。

如果 HBuilderX 真机环境无法持久化 Cookie，优先在 App 请求层增加 Cookie 持久化适配，不修改后端契约，也不把 token 打印到日志。

### 6.2 聊天 SSE

当前聊天接口是 `text/event-stream`，Web 使用 `fetch().body.getReader()` 增量解析。HBuilderX 4.87 的 `uni.request` 不能直接假定具有 Web Fetch 的 `ReadableStream` 行为，因此聊天必须先做技术验证：

- App 端使用 `plus.net.XMLHttpRequest` 或可用的原生网络流接口逐行解析 `data:`。
- H5 预览继续使用 `fetch` 方案。
- 如果当前运行基座无法可靠读取流，保留同一后端接口，使用原生网络适配层，不修改 FastAPI。
- 发送中、超时、每日次数限制、模型不支持图片和流式错误都要有明确状态。

### 6.3 自律与健康数据

首版完整支持现有 Web 已支持的手动打卡、图片上传、AI 饮食/运动分析、日历、报告和 Apple Health 文件导入。

Android 原生健康数据来源不是 Apple Health。为了保持 Web 不受影响：

- 第一阶段使用手动输入和现有导入文件能力。
- 第二阶段评估 Health Connect 原生插件，把步数、活动能量和体重转换为现有 `/discipline/shortcut-sync` 数据结构。
- 不在第一版承诺自动读取 Android 健康数据，除非真机权限、插件和数据映射验证通过。

### 6.4 图片和文件

- 使用 `uni.chooseImage`、`uni.chooseFile` 或 HBuilderX 对应 App API。
- 图片上传统一走 `/api/upload`，上传成功后保存后端返回 URL。
- 相册照片使用压缩、进度、失败重试和剩余容量提示。
- 不把 localhost、127.0.0.1 或本机文件路径写入用户可见 URL。

## 7. 页面通用交互规范

- Android 返回键：详情页返回列表，编辑页先提示保存/放弃，根页面退出前二次确认。
- 所有列表支持加载中、空状态、网络失败、重试和权限不足状态。
- 删除空间、相册、照片、记录、会话等不可逆动作必须二次确认。
- 下拉刷新只用于列表和总览，不对编辑器页面强制刷新。
- 图片预览支持手势缩放、左右切换和系统分享。
- 上传和 AI 生成期间显示可取消或明确不可重复提交的状态。
- 所有用户可见错误统一中文化，保留后端错误语义，不展示堆栈、Cookie 或内部地址。

## 9. 分阶段开发计划

按一名开发者估算，包含编码、接口联调和真机测试，不包含应用市场审核等待：

### 阶段 0：技术验证与后端增量设计，2–3 个工作日

- HBuilderX 项目结构、AppID、Android 包名和签名配置。
- 底部导航和登录态切换。
- Cookie 登录/刷新/退出真机验证。
- 聊天 SSE 流式读取验证。
- 图片上传和 Android 返回键验证。
- MCP 能力查询、用户权限开关和后端编排接口设计。
- DOCX/PDF 解析基准测试、大小限制和临时文件清理验证。

阶段 0 任一项失败，先解决技术底座再进入页面批量开发。

### 阶段 1：用户可用 MVP，8–12 个工作日

- 前厅公开内容首页。
- AI 聊天和会话管理。
- 多模态素材上传、DOCX/PDF 解析任务和 AI 草稿。
- 按权限生成博客或空间文章，发布预览和确认。
- 空间列表、创建/加入、空间概览。
- 书房收藏和博客阅读。
- 登录、注册、邀请申请、我的和退出。
- 基础相册、记录和聊天。

### 阶段 2：Web 用户功能完整迁移，7–11 个工作日

- 相册上传/预览/删除和配额。
- 记录编辑锁、heartbeat、只读降级。
- 聊天模型切换、图片附件、SSE 错误恢复。
- 自律健康档案、日历、手动打卡、AI 分析和报告。
- Apple Health 文件导入、深链邀请和系统分享。

### 阶段 3：写作与超级管理员，5–8 个工作日

- 移动端文章管理和 Markdown 写作/预览。
- 站点资料、媒体卡片、链接和上传管理。
- 用户权限、邀请代码、存储配额、AI 配置。
- MCP Token 管理、博客导入和访问分析。

完整覆盖 Web 用户功能、AI 多模态创作和管理员功能，预计 24–36 个工作日。若只做阶段 1 MVP，预计 8–12 个工作日。以上不包含新原生插件开发和应用市场审核。

## 10. 验收标准

- 未登录、已登录、权限不足、账号禁用和登录过期路径都可完成闭环。
- 底部导航在 390px 手机宽度无横向溢出，Android 返回键行为明确。
- Web 现有公开 API 和管理 API 未被修改。
- 空间、相册、记录、聊天、自律和博客的核心读写操作均可在真机完成。
- 图片上传不显示本地地址，失败可重试，容量超限有明确提示。
- 聊天可显示增量回复，流式失败不会丢失用户已发送内容。
- 管理功能只对 root 用户显示，普通用户无法通过页面入口进入。
- Release APK 关闭调试日志，使用正式 HTTPS、签名和应用图标。

## 11. 本次请审核的决策

建议审核通过以下默认方案后再进入目标模式：

1. Android 采用“前厅 / AI / 空间 / 我的”四项底部导航。
2. 书房从底部导航移除，通过前厅和我的进入；博客保留在前厅内容流中。
3. AI 工作台同时承担聊天、多模态素材整理和文章生成预览。
4. 博客文章走公开博客模型，空间文章走空间记录模型，二者可见性明确分开。
5. 允许增加后端和数据库，但只采用向后兼容的新增表、字段和接口，现有 Web 功能不受影响。
6. Android 发布到博客、空间、相册的内容与 Web 共用数据；AI 会话、解析任务和草稿可以先只在 Android 展示。
7. 先做阶段 0 技术验证，再做阶段 1 MVP，避免在 Cookie、SSE、MCP 权限和文件解析未验证前批量开发。

如方案通过，下一步进入目标模式，按阶段 0 开始执行，并在阶段 0 结束时提交真机验证结果后再继续阶段 1。
