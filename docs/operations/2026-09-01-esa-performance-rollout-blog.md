# 我把 2C2G 个人站点的公共流量搬到了 ESA 边缘：缓存、限流、原子部署与 150 项回归实战

个人站点的性能问题，经常不是“某个函数太慢”这么简单。尤其当服务器只有普通带宽和 2 核 2G 内存时，页面刷新、Service Worker、Next.js 构建、Nginx 压缩、数据库写入与 CDN 缓存会互相影响：一处策略不清楚，就可能出现页面刷新看不到新内容、公共请求反复回源、私有数据被错误缓存，甚至一次前端构建把正在运行的版本变成半成品。

Lumino 的这一轮优化没有从高风险重构开始，而是坚持一个顺序：先修正刷新与缓存正确性，再减少传输体积，然后把明确安全的匿名读取搬到阿里云 ESA 边缘，最后才拆分文章详情的读写路径。整个过程还配套了自动化验证、生产低频回归和文档治理，确保“已经写进代码”不等于“已经在线验证”。

最终结果不是一句笼统的“网站变快了”，而是一组可以复现的变化：公共精选接口压缩样本从约 14.4 KB 降到约 1.94 KB；匿名公共 API 从每次 `DYNAMIC` 回源变成首次 `MISS`、重复 `HIT`；文章详情 GET 不再同步写浏览量；前端构建改为临时目录完成后原子切换；同时 Cookie、Authorization、HTML、RSC 和私有 API 仍然严格绕过公共缓存。

## 一、为什么“刷新慢”首先是正确性问题

项目使用 Next.js 14 App Router，并通过 `next-pwa` 生成 Service Worker。早期默认运行时策略会缓存同源 GET API、页面导航、Next data 与其他运行时资源。对纯静态站点而言，这可能改善离线体验；但对包含登录、私密空间、后台、聊天和频繁更新内容的应用而言，风险远大于收益。

典型问题包括：

1. 用户普通刷新时，浏览器可能优先读到 Cache Storage 中的旧页面或旧 API 响应，误以为部署没有生效。
2. 用户退出账号后，旧用户数据仍可能留在浏览器运行时缓存中；断网时甚至可能重新读到。
3. Service Worker 的缓存不受 ESA `no-store` 自动约束。边缘节点不缓存，不代表浏览器 Cache Storage 不缓存。
4. 默认预缓存会在首次访问后台下载用户尚未访问的路由资源，对普通带宽和移动网络没有必要。

因此第一步不是“给所有东西加缓存”，而是明确禁止错误缓存：

- 页面导航、HTML、RSC、`/_next/data/**` 与所有 `/api/**` 使用 `NetworkOnly`。
- 关闭起始页和前端导航主动缓存，不在首访时预取整站路由 chunk。
- 只有带 content hash 的 `/_next/static/**` 在实际访问后使用 `CacheFirst`。
- 新 Service Worker 激活时删除旧版 `apis`、`others`、`start-url`、`next-data`、`static-data-assets` 等历史运行时缓存。
- `/sw.js` 自身继续保持 `no-store`，确保浏览器能及时检查新版本。

这里的目标不是追求离线页面数量，而是建立一条更重要的安全规则：页面和用户数据只认当前网络响应，不把私密内容变成跨会话的浏览器公共资产。

## 二、低配服务器最怕的不是构建慢，而是构建污染线上目录

Next.js 默认把构建产物写进 `.next`。如果生产进程正在读取这个目录，同时部署脚本直接运行 `npm run build`，就可能出现新旧 chunk 混杂。构建一旦失败，目录里还会残留半成品，随后即使重启 PM2，也可能产生 500 或 `ChunkLoadError`。

这次把发布流程改成了临时构建目录：

```text
当前线上版本：.next
        │
        ├── npm run build → .next-build
        │                    │
        │                    ├── 失败：删除临时目录，线上版本不动
        │                    └── 成功：停止前端进程
        │                              ↓
        └──────────────────── 原子替换 .next 后重启
```

生产发布时，这个设计真的经受了一次现实测试：2C2G 服务器上的 Next.js 静态页面生成超过了 60 秒，构建 worker 被框架终止并自动重试。整个过程持续数分钟，但旧 `.next` 一直继续服务，没有被半成品覆盖；重试最终完成 23/23 页面生成后，部署脚本才切换目录并重启进程。

这也是为什么“原子部署”不是抽象的工程洁癖。低配服务器出现慢构建是正常情况，真正需要控制的是慢构建不能把站点一起拖下水。

## 三、先减少无效字节，再讨论 CDN 命中率

博客首页原有精选接口返回完整文章模型，其中包含 Markdown 正文。卡片实际只需要标题、摘要、封面、分类、标签和发布时间，却要下载整篇正文。优化后新增了轻量公共响应模型，列表和精选接口不再返回 `content`。

生产同一网络环境下的压缩响应样本：

- 旧精选接口：约 14,429 B。
- 新公共精选接口：约 1,943 B。
- 降幅：约 86.5%。

与此同时，Nginx 对 HTML、JSON、JavaScript、CSS、SVG 和纯文本启用 gzip，压缩级别 5，最小长度 1024 B。SSE 路由明确关闭 gzip 和代理缓冲，避免聊天流式输出被积攒后一次性发送。

链路上还发现一个容易忽略的问题：后端、Nginx 与代理层都可能添加 `Vary: Accept-Encoding`。重复的 `Vary` 虽然不一定马上导致故障，却会让缓存键和代理行为变得难以判断。最终配置只由 Nginx `gzip_vary` 负责生成，线上文章详情实测只有一个 `Vary: Accept-Encoding`。

## 四、建立 `/api/public/**`：缓存之前先把身份边界写进 URL

“公开页面”不等于“所有 API 都可以缓存”。如果同一个接口有时匿名、有时根据 Cookie 返回用户数据，那么只依靠某个响应头很难长期保证安全。因此项目新增了独立的 `/api/public/**` 命名空间，并把它定义为一个严格契约：

1. 只允许 GET/HEAD 读取，不产生业务副作用。
2. 不依赖 Cookie、Authorization 或登录用户。
3. 不返回 `Set-Cookie`。
4. 前端调用时省略身份凭据。
5. 成功响应统一使用 `Cache-Control: public, max-age=0, s-maxage=60, stale-while-revalidate=120`。

前厅、书房和博客的公开站点资料、分类、精选、分页与详情逐步迁移到这个命名空间。旧接口继续保留，避免破坏 MCP、后台或历史客户端。

这种设计把安全审查从“猜一个接口在什么情况下公开”变成“只有明确进入 public 命名空间的只读接口才有资格被边缘缓存”。未来新增接口时，路径本身就提醒开发者完成无身份、无副作用和无 Cookie 的检查。

## 五、在 ESA 5 条缓存规则限制内完成动静分流

当前控制台实际只能使用 5 条缓存规则，因此不能简单地为每个新接口继续增加规则。最终规则采用合并与兜底策略：

1. 核心绕过：Cookie、Authorization、后台和其他私有路径优先绕过缓存。
2. HTML 绕过：页面与动态文档不进入公共缓存。
3. 公开图片：明确公开的图片路径允许缓存。
4. 可缓存公共资源：`/_next/static/`、`/workbox-` 与匿名 `/api/public/` 遵循源站缓存头。
5. 默认绕过：所有未明确放行的请求继续 `DYNAMIC`。

关键变化是核心绕过规则不再用一个笼统的 `/api` 匹配全部接口，否则它会在公共缓存规则之前截住 `/api/public/**`。私有 API 并没有因此失去保护，因为默认绕过规则仍然兜底；带身份信息的公共路径请求也会被最前面的 Cookie/Authorization 条件拦截。

缓存键保留完整查询参数。分页、分类、搜索和不同探针请求首次分别返回 `MISS`，不会把一个筛选结果返回给另一个查询。

## 六、ESA 单 IP 200 次/10 秒限流：能做，但要区分“已配置”和“已压测”

ESA 可以直接在边缘按客户端 IP 统计请求频率。官方“频率控制规则”支持按请求特征和相同客户端 IP 计数，在超过阈值后执行观察、挑战或阻断；官方智能限流文档中，“中等”档的初始阈值正是每个 IP 200 次/10 秒。

本项目已由管理员在 ESA 侧配置单 IP 200 次/10 秒限流。它的价值在于异常流量可以在边缘处置，而不是先消耗 2C2G 源站的连接、CPU 和数据库资源。当前 FastAPI 与生产 Nginx 没有额外的 `limit_req`、SlowAPI 或类似单 IP 页面限流，因此不会出现两层规则阈值冲突。

但这里必须严格区分证据：

- **已配置**：管理员确认 ESA 已设置 200 次/10 秒/单 IP。
- **已验证正常流量**：低频访问、公共缓存、Cookie 隔离和页面访问均未被误伤。
- **尚未压测触发**：本次没有为了证明规则而对生产站点发送 201 次突发请求，因为这可能封禁当前出口 IP、制造无意义负载并干扰真实用户。
- **动作以控制台为准**：超过阈值后究竟是观察、JavaScript/滑块挑战还是阻断，以及是否自动调整，应以 ESA 当前控制台配置和命中日志为准。

这不是验证不完整，而是生产验证的边界：能够通过低风险证据确认的就自动化确认；需要主动攻击生产环境才能证明的内容，必须留到受控窗口或测试域。

官方参考：

- [阿里云 ESA 频率控制规则](https://www.alibabacloud.com/help/en/edge-security-acceleration/esa/user-guide/frequency-control-rules)
- [阿里云 ESA 智能限流](https://www.alibabacloud.com/help/en/edge-security-acceleration/esa/user-guide/smart-rate-limiting)

## 七、文章详情读写分离：让 GET 重新成为真正的读取

旧文章详情 GET 会在读取正文时同步执行 `view_count += 1`。这带来三个问题：

1. GET 产生数据库写事务，不再是幂等读取。
2. 每次阅读都会触发源站和数据库，无法安全地在 ESA 缓存。
3. 页面刷新、预取或爬虫访问都可能制造无意义浏览量写入。

改造后，公开详情使用 `/api/public/blog/posts/{slug}` 纯只读接口；浏览量单独通过 `POST /api/blog/posts/{slug}/view` 上报并返回 204。浏览器使用 LocalStorage 按文章保存最近上报时间，30 分钟内重复访问不再提交。

后端回归测试验证了两次连续 GET 的 `view_count` 都保持为 5，显式 POST 后才变为 6；不存在的文章写入返回 404。线上真实文章也验证了详情第一次 `MISS`、第二次 `HIT`，浏览量 POST 返回 204。

## 八、验证不是一条 curl，而是一组隔离断言

项目新增 `scripts/verify-esa.sh`，每次执行使用新的查询探针，覆盖：

- 前厅、书房、博客、Service Worker、健康接口和私有 API 必须保持 `DYNAMIC`。
- 图标与真实 `/_next/static/*` 资源必须在热请求下出现 `HIT`。
- 公共 API 必须首次 `MISS`、重复 `HIT`，并返回 60 秒边缘 TTL。
- 不同查询参数必须分别首次 `MISS`。
- 同一公共 URL 带 Cookie 后必须返回 `DYNAMIC`。
- 文章详情必须 gzip，并且只出现一个 `Vary: Accept-Encoding`。
- 浏览量写入必须独立返回 204。

## 九、哪些内容没有做，以及为什么主动冻结

优化方案仍然留下 8 项工作：旧 Service Worker 升级和离线用户隔离的浏览器验证、LCP/CLS/INP 多轮采样、图片懒加载量化、博客分类切换请求取消统计、ESA 主动 Purge、上传期缩略图、博客首页聚合接口，以及 ISR/Server Component/多进程短缓存评估。

这些项目已经写入根目录 `TODO.md` 并默认冻结。除非管理员明确点名某一项，否则 Agent 不会主动实施，也不会借其他任务“顺手优化”。原因很现实：当前核心中低风险优化已经解决刷新错误、重复回源、响应冗余、文章读写耦合和构建污染；继续推进结构性改造，需要新的浏览器基线、资源预算和一致性设计，不应该为了追求一个更大的完成百分比而增加系统复杂度。

## 十、最终得到的不是一套缓存技巧，而是一套可审计边界

这次实践最重要的经验有四条：

第一，缓存优化必须从“哪些绝对不能缓存”开始。用户数据、页面导航、RSC 与身份请求的正确性比离线命中率更重要。

第二，边缘缓存不是简单地把 `/api` 全部设为 public。先建立匿名只读命名空间，再让 ESA 只缓存这个明确集合，才能把性能收益和隐私风险解耦。

第三，低配服务器的可靠性优化往往比微小的运行时加速更值钱。一次慢构建不可怕，慢构建污染线上版本才可怕；原子切换把不可控的构建耗时变成了可控发布过程。

第四，文档必须区分 implemented、verified、planned 和 user-confirmed。`200 次/10 秒` 限流已经配置，但没有生产突发压测；公共 API `MISS → HIT`、Cookie 隔离、gzip 与 204 写入则已经通过真实请求验证。只有保持这种边界，下一位开发者或 Agent 才不会把旧方案、控制台意图和线上事实混成一件事。

对于一台普通带宽、2C2G 的个人服务器而言，最有效的策略不是把所有计算都塞进源站，也不是无限增加缓存，而是让公开、可复用、无身份的数据尽量停留在边缘；让私有请求与写操作保持清晰、可追踪的回源路径；再用自动化脚本证明两者没有串线。
