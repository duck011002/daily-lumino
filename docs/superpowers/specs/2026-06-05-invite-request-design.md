# Lumino 邀请码注册与申请链路设计

> **历史设计参考：** 本文保留当时的设计取舍，不能代替当前实现说明。请先阅读 `docs/features/auth-invite/current.md` 与 `implement.md`。

日期：2026-06-05

## 1. 背景

当前 Lumino 的注册页显示“邀请码（可选）”，但后端实际已经具备邀请码校验能力，前后端语义并不一致。用户不填写或填写错误时，前端错误展示还有机会出现 `[object Object]`，注册体验不够稳定。

本次设计目标是在不破坏现有产品风格和代码组织方式的前提下，把注册流程调整为“邀请码必填”，并补齐一条站内邀请码申请链路：

- 用户在站内提交申请表单
- 系统先验证申请邮箱所有权
- 只有邮箱验证通过后，才通知管理员固定邮箱
- 管理员通过邮件中的链接批准或拒绝申请
- 批准后系统自动生成邀请码并发送给申请人

## 2. 目标

- 把注册页的邀请码从可选改为必填
- 在注册页提供清晰的“没有邀请码？去申请 ~”入口
- 提供一条独立的邀请码申请流程，不要求用户手动给管理员发邮件
- 防止未验证邮箱的垃圾申请直接打到管理员邮箱
- 对管理员通知邮件施加全局节流：每 60 秒最多发送 1 封
- 防止系统被滥用去骚扰第三方邮箱
- 复用现有 `invite_codes` 能力，避免引入不必要的复杂度
- 所有注册和申请相关错误都返回可读文本，不向前端暴露对象结构

## 3. 非目标

- 本次不重做管理员后台整体 UI
- 本次不引入复杂的多级审核或人工工单系统
- 本次不支持一个邀请码多人复用
- 本次不设计短信或即时通讯审批链路
- 本次不改变现有登录、登出、Refresh Token 机制

## 4. 现状摘要

### 4.1 前端

- 注册页位于 `frontend/src/app/register/page.tsx`
- 页面当前把 `inviteCode` 标为可选
- 表单提交时会把 `invite_code` 处理为 `inviteCode.trim() || null`
- `useAuth.register()` 通过 `frontend/src/lib/api.ts` 调后端 `/api/auth/register`
- `getErrorMessage()` 已具备一定的错误提取能力，但在 `detail` 为对象时会退化到 `JSON.stringify(detail)`，页面层仍可能收到不理想展示内容

### 4.2 后端

- 注册接口位于 `backend/app/routers/auth.py`
- `UserCreate` 中 `invite_code` 当前为可空
- 注册接口只在 `invite_code` 有值时才检查邀请码有效性，因此后端当前允许无邀请码注册
- 后台已存在根管理员生成邀请码的能力，位于 `backend/app/routers/admin.py`
- 邀请码模型 `InviteCode` 已支持：
  - 创建人
  - 使用人
  - 过期时间
  - 使用时间
- 项目配置中已存在 `REDIS_URL`，但目前尚未接入任何限流或队列逻辑
- 项目尚无现成邮件发送服务

## 5. 总体方案

采用“方案 2”作为正式设计：

1. 用户在站内申请邀请码
2. 系统只先给申请邮箱发送验证邮件
3. 用户点击验证链接后，申请进入待管理员审核状态
4. 系统将申请放入“管理员通知队列”
5. 队列按全局节流规则向固定管理员邮箱发送审批邮件
6. 管理员点击批准链接后，系统创建一个新的邀请码
7. 新邀请码绑定申请邮箱，并发送到申请人的邮箱
8. 申请人通过邮件中的注册链接完成注册

这条链路保留了“管理员在邮箱中点链接完成审批”的工作方式，同时显著降低了乱填邮箱和垃圾申请对管理员邮箱的冲击。

## 6. 用户体验设计

### 6.1 注册页调整

注册页继续沿用现有视觉结构、卡片、背景光斑、输入框和按钮样式，只做局部调整：

- 将“邀请码（可选）”改为“邀请码 *”
- 邀请码输入框改为必填
- 邀请码输入框下增加一行弱化说明文案：`没有邀请码？去申请 ~`
- “去申请 ~” 跳转至独立邀请码申请页

如果用户是从邀请码邮件中的注册链接进入注册页：

- 自动填充 `email`
- 自动填充 `invite_code`
- `email` 默认锁定为只读，避免用户误改
- `invite_code` 可显示为已填充状态，保持“邀请码必填”的认知一致性

### 6.2 邀请码申请页

新增独立申请页，延续注册页风格，字段保持克制：

- 邮箱：必填
- 用户名或称呼：选填
- 申请说明：选填

申请页不展示复杂流程说明，只保留简洁文案，例如：

- 标题：申请邀请码
- 副文案：验证邮箱后，我们会将申请发送给管理员审核

### 6.3 申请提交后的反馈

提交申请后，前端统一提示为：

- `如果该邮箱可以接收申请邮件，请查收并完成邮箱验证`

这里不暴露“邮箱是否已存在”“是否超限”“是否已在冷却中”的精确信息，避免被用来探测系统策略。

### 6.4 管理员审批方式

管理员无需进入后台即可完成首轮处理：

- 审批邮件中显示申请摘要
- 提供“批准并发送邀请码”链接
- 提供“拒绝申请”链接

管理员点击链接后，浏览器打开一个简单结果页：

- 批准成功：显示“邀请码已发送至申请邮箱”
- 拒绝成功：显示“申请已拒绝”
- 链接失效：显示“审批链接已失效，请重新处理待审申请”

### 6.5 申请人收码方式

管理员批准后，系统向申请人发送邀请码邮件，包含：

- 邀请码
- 有效期
- 注册链接

注册链接直接带上 `email` 与 `invite_code` 查询参数，减少用户重复输入。

## 7. 数据模型设计

### 7.1 保留现有模型

继续使用现有 `invite_codes` 表作为最终可注册的邀请码存储，不另起一套邀请码模型。

### 7.2 新增申请模型

新增 `invite_requests` 表，用于承载从“提交申请”到“管理员审批”的全过程。

建议字段如下：

- `id`
- `email`
- `display_name`
- `message`
- `status`
- `verify_token_hash`
- `verify_token_expires_at`
- `verified_at`
- `admin_notified_at`
- `admin_action_token_hash`
- `admin_action_expires_at`
- `approved_at`
- `rejected_at`
- `invite_code_id`
- `request_ip`
- `user_agent`
- `created_at`
- `updated_at`

### 7.3 状态机

状态保持最小集合：

- `pending_verify`
- `pending_admin_review`
- `approved`
- `rejected`
- `expired`

状态迁移规则：

- 新申请创建后：`pending_verify`
- 用户点邮箱验证链接后：`pending_admin_review`
- 管理员批准后：`approved`
- 管理员拒绝后：`rejected`
- 验证链接或审批链接超时且未完成时：`expired`

## 8. 邀请码约束设计

管理员批准后创建的邀请码继续保持现有“一次性使用”语义，并增加以下约束：

- 邀请码绑定申请邮箱
- 邀请码只能用于该邮箱注册
- 邀请码建议设置过期时间，默认 48 小时

因此需要在现有邀请码能力上补充“绑定邮箱”概念。最直接的设计是给 `invite_codes` 增加一个可空字段，例如 `target_email`，仅用于申请批准后生成的邀请码。

规则如下：

- 管理员后台手动生成的邀请码可以不绑定邮箱
- 通过申请流程自动生成的邀请码必须绑定邮箱
- 注册时如果 `invite_code.target_email` 有值，则 `user_in.email` 必须与之完全一致

## 9. 接口设计

### 9.1 需要新增的公开接口

- `POST /api/auth/invite-requests`
  - 提交邀请码申请
- `GET /api/auth/invite-requests/verify`
  - 处理申请邮箱验证链接
- `GET /api/auth/invite-requests/admin-action`
  - 处理管理员邮件中的批准或拒绝动作

### 9.2 需要调整的现有接口

- `POST /api/auth/register`
  - 邀请码改为必填
  - 必须校验邀请码存在、未使用、未过期
  - 如果邀请码绑定了邮箱，必须校验与注册邮箱一致

### 9.3 可选的后台接口

如果后续希望后台可见申请列表，可额外新增：

- `GET /api/admin/invite-requests`
- `POST /api/admin/invite-requests/{id}/resend`

但这两项不是本次闭环的必需项，可作为后续增强。

## 10. 邮件链路设计

### 10.1 申请人验证邮件

触发时机：

- 用户提交申请成功后

内容要求：

- 明确说明这是邀请码申请邮箱验证邮件
- 包含单次使用的验证链接
- 有效期默认 30 分钟

### 10.2 管理员审批邮件

触发时机：

- 申请完成邮箱验证后，进入待通知管理员队列

内容要求：

- 申请邮箱
- 用户名或称呼
- 申请说明
- 申请时间
- 邮箱验证完成时间
- 脱敏后的来源 IP
- 批准链接
- 拒绝链接

### 10.3 申请人邀请码邮件

触发时机：

- 管理员批准申请后

内容要求：

- 邀请码
- 过期时间
- 注册链接
- 说明该邀请码仅可用于当前申请邮箱，且只能使用一次

## 11. 反滥用与限流设计

### 11.1 设计原则

滥用防护分为两类：

- 保护管理员邮箱不被垃圾申请轰炸
- 保护第三方邮箱不被系统滥用为骚扰通道

### 11.2 关键防线

第一道防线：先验证邮箱，再通知管理员

- 未完成邮箱验证的申请，不允许进入管理员通知阶段

第二道防线：管理员通知队列全局节流

- 给固定管理员邮箱发审批邮件时，全局每 60 秒最多发送 1 封
- 超出速率的申请进入队列等待，不直接丢弃

第三道防线：同邮箱去重与冷却

- 同一个邮箱同时只保留 1 条未完成申请
- 60 秒内不重复发送验证邮件
- 10 分钟内只允许 1 次有效申请
- 24 小时内最多 3 次有效申请

第四道防线：同 IP 限流

- 10 分钟内最多 3 次申请提交
- 24 小时内最多 10 次申请提交

第五道防线：轻量机器人拦截

- 前端增加隐藏蜜罐字段
- 前端或后端校验表单提交耗时不得短于 2 至 3 秒

第六道防线：预留可选人机校验

- 如果后续线上攻击明显，可引入 Cloudflare Turnstile 一类的人机校验
- 该项不是第一版必需项，但设计上应预留接入点

### 11.3 Redis 用途

项目已有 `REDIS_URL` 配置，第一版建议用 Redis 承担如下职责：

- 邮箱限流计数
- IP 限流计数
- 管理员通知发送节流
- 待通知管理员的简单队列状态

如果 Redis 不可用：

- 申请提交流程可降级为数据库逻辑加较弱限流
- 管理员通知队列不得静默失效，应记录错误并允许后台重试

## 12. Token 与安全设计

### 12.1 Token 原则

申请邮箱验证链接和管理员审批链接都使用随机高熵 Token。

数据库中不存原始 Token，只存 `hash`。

### 12.2 验证链接

- 单次使用
- 默认 30 分钟过期
- 使用成功后立即失效

### 12.3 管理员审批链接

- 单次使用
- 默认 24 小时过期
- 与具体申请绑定
- 成功批准或拒绝后立即失效

### 12.4 管理员动作保护

管理员审批链接本身已经具备高熵和一次性特征，因此第一版可以不要求管理员再次登录。

但系统必须：

- 校验 Token
- 校验状态必须为 `pending_admin_review`
- 校验未过期
- 校验未被使用

## 13. 错误处理与文案

注册与申请链路中的错误文案统一返回可读文本，不把对象直接传给用户。

关键文案建议如下：

- 未填写邀请码：`请输入邀请码`
- 邀请码无效或已使用：`邀请码无效或已使用`
- 邀请码已过期：`邀请码已过期`
- 邀请码邮箱不匹配：`该邀请码仅可用于申请时填写的邮箱`
- 申请提交成功：`如果该邮箱可以接收申请邮件，请查收并完成邮箱验证`
- 验证链接失效：`验证链接已失效，请重新申请`
- 审批链接失效：`审批链接已失效，请重新处理待审申请`
- 申请过于频繁：`操作过于频繁，请稍后再试`

前端 `getErrorMessage()` 仍可保留，但不应再让页面直接展示对象序列化结果。页面层和接口层都应确保最终给用户的是人类可读字符串。

## 14. 异常与补偿策略

### 14.1 验证邮件发送失败

- 申请记录保留为 `pending_verify`
- 前端返回统一失败文案
- 同邮箱在冷却后允许重发验证邮件

### 14.2 管理员通知邮件发送失败

- 申请状态保持 `pending_admin_review`
- 申请继续保留在待通知队列中
- 允许后台重试，不得丢单

### 14.3 批准后邀请码邮件发送失败

- 不重复生成邀请码
- 申请状态保持 `approved`
- 记录 `invite_code_id`
- 后续只重发邀请码邮件

### 14.4 重复审批

- 同一审批链接被再次点击时，不重复生成邀请码
- 直接返回“该申请已处理”或“审批链接已失效”

## 15. 测试范围

### 15.1 前端

- 注册页邀请码字段为必填
- 注册页展示“没有邀请码？去申请 ~”
- 注册错误不再显示 `[object Object]`
- 从邮件注册链接进入时，`email` 与 `invite_code` 自动填充

### 15.2 后端

- 无邀请码注册失败
- 无效邀请码注册失败
- 过期邀请码注册失败
- 已使用邀请码注册失败
- 邀请码绑定邮箱不匹配注册失败
- 提交申请后仅发送验证邮件，不通知管理员
- 验证成功后进入待管理员审核状态
- 管理员通知满足“每 60 秒最多 1 封”
- 批准后生成一次性邀请码并绑定申请邮箱
- 拒绝后申请状态变更正确
- 各类 Token 过期、重复使用、状态错误时返回正确文案

## 16. 分阶段实施建议

建议按以下顺序实现，降低回归风险：

1. 调整注册页前后端：邀请码必填、错误文案收口、邮箱绑定校验
2. 引入 `invite_requests` 数据模型与申请提交接口
3. 接入申请邮箱验证邮件
4. 接入管理员通知邮件与全局节流
5. 接入批准后自动生成邀请码与发码邮件
6. 补齐测试与边界补偿逻辑

## 17. 最终决策摘要

- 采用站内申请表单，不采用用户手动发邮件
- 采用“先验证申请邮箱，再通知管理员”的两段式链路
- 管理员邮件采用全局队列节流，每 60 秒最多 1 封
- 邀请码改为注册必填
- 通过申请流程生成的邀请码绑定申请邮箱，并默认 48 小时过期
- 不引入重型审核系统，优先复用现有邀请码体系与项目现有风格
